## S10A command contract

- `POST /api/v1/tasks/:id/wait`: strict body `{ expectedVersion, reason, delayCause, responsibleParty? }`. Reason and delay cause: trimmed 3–1000 characters; optional responsible party: trimmed 1–160 characters. Requires live session, exact origin, CSRF, current task access, primary owner or Owner, IN_PROGRESS, active permitted project/closeout approval and no exit reassignment gate.
- `POST /api/v1/tasks/:id/resume`: strict body `{ expectedVersion, reason }`. Requires the same current authority and gates, ordinary WAITING and a saved IN_PROGRESS state; it restores that exact saved state and clears current waiting fields. No implicit completion or review bypass.
- `GET /api/v1/tasks/:id` returns current waiting fields, status history containing delayCause/responsibleParty for the wait/resume evidence, and boolean capabilities `wait` and `resume`. Existing progress/edit/reassign capabilities remain backward-compatible.

The current task retains waiting metadata only while Waiting. Immutable history keeps the original cause and party after resume, reassignment, employee exit or cancellation. Existing C-023 forced waiting retains its required owner and reassignment gate and does not need an ordinary delay cause. Reassigning ordinary waiting changes the owner without silently resuming it. Employee exit replaces current ordinary waiting with exit waiting in the same transaction; terminal cancellation clears current waiting and retains historical evidence.

## S10B committed-date increment — R-023.b

In scope: a separate optional committed due date for open non-closeout tasks, initial setting and subsequent distinct-date changes by the Owner or explicitly granted, currently scoped management actor. Each change requires a reason and expected version, records old/new date, actor, time and task version in append-only history, and commits canonical `task.deadline_changed` audit/event/outbox evidence atomically. The existing target date remains independent operational planning data; the ordinary edit command never writes the commitment.

Out of scope for S10B: employee extension requests and approval routing (R-023.c; the Owner subsequently chose employee-selected eligible scoped manager/Owner approvers); date clearing or moving a commitment without a replacement; notifications/reminders and derived overdue views; C-016 closeout deadlines, since their approved work scope includes a due date and changing it through this separate path could bypass closeout approval; S10C dependencies and recurrence. No relationship such as committed date ≥ target date is imposed by the approved source.

Staff must have both their existing scoped management access (`task.assign` plus the reporting-tree or project-management/assignment checks) and a separate `task.deadline_change` grant. `task.assign`, job title and Project Lead assignment alone do not confer date authority. For a non-project task the date grant must cover the owner's home Team. For a project task it must cover the project's Branch; current project assignment and view/manage permission still apply, including an explicit cross-Branch grant when needed. Owner retains organization authority. The task must be open, not awaiting C-023 reassignment, and its project must be Active. These conditions are rechecked inside the date transaction. A date-only grant does not expand task-detail visibility or collaborator/history access; any future date-only manager view needs an explicit Owner scope decision.

`POST /api/v1/tasks/:id/committed-date` accepts strict `{ expectedVersion, committedDueDate, reason }`, where the date is an ISO calendar date and reason is trimmed to 3–1000 characters. `GET /api/v1/tasks/:id` adds `task.committedDueDate`, ordered `history.committedDateChanges` and `capabilities.changeCommittedDate`. A duplicate date is a conflict, not an extra historical event. Approval workflow, date extension and client-visible promise policy remain deferred.

S10B acceptance: fresh and S10A-upgrade migration preserve existing rows; manager/Owner allow and ungranted/title-only/cross-team/cross-project/guessed-ID deny; initial and changed dates survive refresh with distinct immutable before/after evidence; terminal/held/exit/closeout tasks deny; stale/concurrent commands conflict; injected audit failure rolls back all writes; forged direct SQL update without matching history fails; TypeScript, lint, relevant unit/HTTP/PostgreSQL/browser checks and build pass. ## S10C dependency design — R-026.a–b / R-025.d

In scope: explicit finish-to-start links where Task B depends on Task A, both tasks belong to the same currently Active project, and neither is an approved closeout task. An incomplete predecessor warns B's owner at start; it does not block starting B after explicit acknowledgement. A completed predecessor needs no acknowledgement. Completing A creates an in-app notice for the current primary owner of each linked B that is in ordinary Waiting, subject to delivery-time authorization. Ordinary Waiting alerts under R-025.c are implemented separately in S10E.

The Owner confirmed that Task B's primary owner or a scoped manager may add/remove a link only with current access to both tasks. The Owner also confirmed same-project links only; non-project and cross-project links are out of scope. A manager's task/project access must be current under S09 rules; a role title or project membership alone confers no link authority. The service must recheck both tasks, their project, actor state/access and B's optimistic version in the transaction. No link action broadens access to the predecessor's title, details or history. The detail response may show an accessible predecessor's identity/status and a generic unfinished-dependency warning when predecessor details are no longer visible.

Proposed API contract: `POST /api/v1/tasks/:id/dependencies` with strict `{ predecessorTaskId, expectedVersion, reason }`; `POST /api/v1/tasks/:id/dependencies/:predecessorId/remove` with strict `{ expectedVersion, reason }`. These are separate commands for B. They return B's new version and current link summary; B's detail adds ordered predecessor summaries, unfinished-warning state and `capabilities.manageDependencies`. Duplicate add, missing remove, self-edge, indirect cycle, mismatched organization/project, inaccessible IDs, held/terminal project and stale B version fail without a partial write. Changes have actor/reason/time and immutable add/remove evidence plus canonical audit/event/outbox in the same transaction. Concurrent opposite-edge insertion must serialize the project graph and cannot create a cycle.

Proposed start contract: `POST /api/v1/tasks/:id/state` retains existing transition fields and accepts `acknowledgeUnfinishedDependencies: true` only for NOT_STARTED → IN_PROGRESS. When any linked A is unfinished at the locked start decision, the command returns a conflict with a safe warning unless this flag is true. Acknowledged early start writes the unresolved predecessor set/count and acknowledgement into the same `task.started` audit/domain event as the state change. The response and UI show the warning before the user confirms; completion still obeys existing review gates. Links added after B started cannot retroactively alter that start event, but remain visible as current unresolved dependencies.

At A completion, one event/notification per linked B that is in ordinary Waiting avoids collapsing distinct B tasks for the same owner. The recipient is the active current primary owner, with exact B ownership, current B/project access and active link checked again when the in-app notice is delivered; exited owners, revoked grants, stopped tasks and no-longer-waiting B must not receive stale notices. The notice conveys only that an authorized dependency completed; it does not resume B automatically. Duplicate delivery/retry is idempotent. Email is not required for this first in-app notice.

S10C acceptance: fresh and S10B-upgrade migrations preserve prior tasks, dates and histories; authorized add/remove persists and appears after refresh, while title-only, non-owner, inaccessible predecessor and cross-project attempts deny; self/indirect/concurrent cycles and duplicate links deny; incomplete A triggers a visible start warning and a second explicit action, with exact audit/event evidence, whereas completed A starts normally; completion of A notifies only a still-authorized Waiting B owner once, and does not resume B; cancellation/exit/reassignment retain safe history and current routing; injected audit failure rolls back link/start/notice changes; SQL evidence/cycle guards and desktop/mobile/API/PostgreSQL tests pass. S10 remains IN PROGRESS pending the remaining R-023.c, R-025.c and recurrence work.

## S10D employee extension design — R-023.c

Approved source: an employee may request a committed-deadline extension with a reason and proposed new date; management separately approves or rejects. The Owner chose only the task's current primary owner as requester, excluding collaborators, and an employee-selected eligible currently scoped manager or Owner as approver. Only an existing committed date can be extended; the proposal must be a valid later calendar date. S10D excludes approved closeout work, terminal/exit-wait tasks and non-Active projects, consistent with S10B's commitment authority.

Proposed persistence: a task-scoped request record retains task/organization, requester, selected approver, previous commitment, proposed date, task version at request, reason, request/decision times and linked S05 ApprovalRequest. Permit one pending extension per task; keep resolved requests and decisions immutable. Request creation must recheck owner access, task/project state, current commitment, the selected approver's live S10B date authority, and non-self-approval within one transaction. ApprovalService type `task.deadline_extension` will produce management queue cards and enforce current approver identity and authority again at decision. Delegation is unavailable in the first increment. Rejection retains the old commitment and records the decision. Approval atomically changes the task committed date through the same history/audit/event path as S10B, with the approved request and decision ID bound to the date change. If the task owner, commitment, project state or approver authority changed, approval fails closed without resolving the request; the manager may reject it or the Owner may handle a documented withdrawal/replacement path. A second independent direct date change cannot be silently overwritten by a stale extension decision.

Proposed API/UI: eligible-approver picker is filtered by the backend, not title; strict request and decision endpoints require session/origin/CSRF/version, and task detail shows current pending request plus ordered request/decision history only to authorized task actors. The primary owner sees a reason/date/approver form when eligible; the selected manager/Owner sees an approval/rejection card with current and proposed dates and reason. Explicit decision text, loading/denial states and refresh persistence are required. Verify cross-team/branch/guessed-ID denial, stale approvals, concurrent requests/decisions, self-approval denial, rejection no-date-change, approved date/history/audit/approval evidence atomicity, injected failure rollback, desktop/mobile and all repository gates before accepting S10D.

The Owner confirmed that links may be added or removed while B remains open. Every edit requires a reason and audit evidence. A task already Waiting may therefore link the actual blocker and receive the R-025.d notice; its earlier start audit describes only links present at the start decision. S10C was implemented after S10B full verification; its local checks and remaining whole-slice work are recorded in S10_PROGRESS_REPORT.md.
