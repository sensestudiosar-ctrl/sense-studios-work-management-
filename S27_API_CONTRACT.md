# S27 bounded evidence-assistance contract

## Internal routes and commands

All routes use the existing current OWNER/STAFF cookie session, OwnerReady and no-store read rules. Every POST additionally requires configured same Origin and current CSRF. CLIENT/EXTERNAL cannot call these routes. UUIDs, strict object schemas, calendar dates, bounded ranges/text and unknown-key rejection follow existing controllers. Command ID is a UUID; identical actor/command/payload replay returns the committed result, changed reuse returns conflict.

| Route | Input | Behavior |
| --- | --- | --- |
| GET /api/v1/ai/context | None | Current role capabilities, currently accessible projects/tasks and supported request kinds; deterministic provider identity and unavailable capability labels. Never an organization-wide employee directory for ordinary staff. |
| POST /api/v1/ai/runs | `{commandId,kind,reason,projectId?,taskId?,from,to,purpose?,broaderSearch?}` | Persist a current-authorized bounded result and return its ID. Kinds DAILY, PROJECT, MANAGEMENT, ASSIGNMENT. Explicit ordered date window is required; bounded maximum 31 days. PROJECT requires projectId; ASSIGNMENT requires taskId and purpose PRIMARY_OWNER/COLLABORATOR/REVIEWER. Assignment scope derives from that exact task; reject a supplied projectId that differs. Other kinds forbid assignment fields. MANAGEMENT requires existing scoped management evidence authority. No arbitrary natural-language prompt or code expression. |
| GET /api/v1/ai/runs | Optional bounded paging cursor | Creator's runs only; Owner may inspect organization runs only after their original source manifest is currently authorized. Listing must not disclose inaccessible titles/subjects. |
| GET /api/v1/ai/runs/:id | Run ID | Reauthorize original full source manifest and request/candidate scope before revealing persisted result. A stale candidate is flagged unavailable; access loss denies/redacts rather than returning retained secrets. |
| POST /api/v1/ai/runs/:id/decisions | `{commandId,expectedDecisionVersion,outcome,reason,selection?}` | ACCEPTED, REJECTED or OVERRIDDEN; typed selection requires `{purpose,employeeId}` for assignment acceptance/override. Requester records a nonbinding current-authorized human decision; Owner may do so only with the same current source/management checks. Ordinary source commands must still finalize the business action. |
| POST /api/v1/ai/runs/:id/outcomes | `{commandId,expectedDecisionVersion,decisionId,taskId,reason}` | Append a verified current source observation linked to a prior decision and actual owning-task evidence. Never change assignment/reviewer or claim observed state was executed by assistance. Deny forged/mismatched project/task IDs. |

Decision version starts at 0; each retained decision/outcome increments the run's decisionVersion under lock. This version is concurrency coordination, not permission or mutable generated content. All reasons are mandatory 3–1000 characters. Only one decision per expected version succeeds; previous decisions remain visible history. Summary decisions forbid assignment selections. Assignment ACCEPTED/OVERRIDDEN decisions require a typed currently eligible selection; REJECTED decisions forbid selection. Manual override may choose a candidate outside the original retained list only after the owning assignment/reviewer port checks the same current requested Team/broader-search scope and ordinary eligibility. Stale/ineligible selections are rejected, never restored by retained evidence. Outcome observations must bind the original run task and a prior ACCEPTED/OVERRIDDEN decision, with current persisted owner/collaborator/reviewer state verified by the owning port. Reauthorize every retained source before exposing result content; candidate staleness can be disclosed only while all retained facts remain authorized, otherwise deny or redact the inaccessible result. Outcome observations describe persisted facts and source version/time rather than inventing causation or success ratings. The 31-day window is a technical bounded-query limit, not an Owner workforce/business calculation policy.

## Output and provider contract

The provider is `deterministic-evidence-v1`, model `none`. Responses explicitly say deterministic evidence assistance; no live inference or external transmission occurs. Interface: immutable typed authorized context → strictly validated structured result. Context includes bounded selected scalar/text values and typed source references only. Source text never authorizes instructions/tools. No provider HTTP endpoint, API key, arbitrary tools, raw media, hidden chain-of-thought or autonomous execution path.

Result contains `kind`, `provider`, `providerVersion`, `generatedAt`, `scope`, `summary`, `facts`, `candidates`, `unavailableFactors` and `limitations`. Facts reference exact manifest entries. Candidates contain employee ID, source-authorized display label, purpose, current Team, eligibility and independent typed factors, not a composite score. Stable display ordering is unranked; never label alphabetical position as recommendation strength. Factor values distinguish observed zero from unavailable setup/data. Do not make unsupported skills/productivity/similar-task/predictive claims.

Current-Team scope derives from the selected task's current recorded owner membership, validated by the owning TaskService port. Broader search defaults false. Explicit true requires current Owner or the existing accepted explicit Team Leader predicate: current project assignment/view, project management, employee management and task assignment in current project scope. TurnkeyService.leader establishes this explicit-management representation; Employee/Owner-dynamic JobRole has no canonical TeamLeader enum, so never match a role display name or treat one loose action grant as leadership. The owning TaskService port must enforce that complete predicate. A task without a supported current Team returns unavailable with explanation. Every displayed or selected candidate must independently pass ordinary current assignment/project eligibility; broader search cannot create project membership or cross-Branch grants. Reviewer purpose additionally uses REV's ordinary independent reviewer eligibility (distinct task owner and eligible current project member). Never recommend a reviewer eligible only by inference from permissions.

## Migration115 plan

Runs retain organization/requester, optional project/task source, request kind/purpose/current-Team/broader flag, provider/version, input digest, immutable structured request/evidence manifest/result, created audit/event identity and monotonic decisionVersion. Decisions retain organization/run, sequential version, kind DECISION/OUTCOME, actor, decision outcome, reason, selection, optional source-linked outcome data and audit/event identity. All nullable references need paired/check constraints appropriate to kind. UUID defaults, timestamps, unique run/version and organization/actor/command indexes and input/result bounds follow existing persistence conventions.
