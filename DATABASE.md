# Database architecture — S01 baseline migration established; business schema not started

Approved architecture specifies a PostgreSQL relational model. Approved source: R-004–R-098 and critical invariants R-092. Approved clarifications C-001–C-024: Organization → Branch → Team → Employee, no separate Brand or Department tier; each project has one owning branch, with later leave, score, CAD, backup, identity and retention policies recorded separately. S01 establishes PostgreSQL connectivity, an empty Prisma business schema and one reviewed baseline SQL migration. Domain names below remain conceptual, not a migration contract.

## Ownership and constraints

- Every business row carries organization_id where relevant. A Branch belongs to one Organization; a Team belongs to one Branch. Branch-owned records carry branch_id. Each Employee has exactly one current home Branch and one current home Team within that Branch, with dated membership history. A project has one owning branch_id; only a formal Owner-approved transfer may change it, preserving the prior owner and recalculating access. Project lead is required at activation and exactly one is current while Active. C-024 permits an On Hold project with no current lead after exit while preserving dated prior-lead history; the exit transaction moves each affected Active project On Hold with reason and audit, then the Owner appoints an eligible replacement before resume. Project cancellation from Draft/Active/On Hold requires an Owner decision, reason and immutable evidence; Cancelled is terminal. C-012 requires confirmed revocation records for active vendor/consultant native CAD links before final cancellation, then atomically ends vendor/consultant app project access. C-013 atomically switches existing client project grants to issued-record read-only mode and withdraws pending client decisions without erasing evidence. C-014/C-015 record cancellation-effective time and a required Owner-set expires_at for each client project-access grant, with audited Owner-approved changes/extensions; no organization-wide duration is assumed. Request-time authorization denies access at each grant's expiry independently of scheduled cleanup. Cross-branch staff may contribute only through explicit project assignment and applicable permission grants issued by the Owner. No Brand or Department foreign key or scope is planned.
- Use stable opaque IDs, foreign keys, unique indexes and check constraints. Composite references including organization/branch where practical prevent linking a task, document or approval to a foreign project accidentally. Scope-sensitive queries must be authorized before reads/writes; consider RLS as defense in depth after testing its interaction with the access model.
- C-020 records a named verifier for each snag, its appointing Project Lead/authorized Team Leader, and each verification attempt with outcome, reason/evidence, actor and time. A verifier cannot be the person recorded as performing the repair; changing verifier preserves history. Failed verification returns the same snag to In Progress without erasing the failed attempt. C-021 requires a separate Verified-to-Closed decision by the assigned Project Lead or explicitly authorized Team Leader, with closer, time and evidence; no close without a current passed verification.
- C-023 employee exit keeps the inactive employee as the current primary owner on each unfinished task while atomically setting Waiting with a needs-reassignment reason and prior-state snapshot. The task cannot advance until an authorized manager explicitly selects a permitted replacement; reassignment and resume retain the old owner, prior state, approvals, time and review history. Completed/terminal tasks stay unchanged; an exception queue and deadline alerts expose waiting work.
- A task row has one non-null primary_owner_id. Collaborators and per-person effort allocation live in separate association rows, unique by task/person. Dependency edges prohibit self-dependency/cycles; unfinished predecessors warn rather than block. C-011 adds a terminal stopped-for-project-cancellation outcome for unfinished delivery tasks, with cancellation linkage and preserved history; distinct closeout tasks may reference a Cancelled project only with C-016 approval evidence from its assigned Project Lead or an explicitly authorized Team Leader.
- C-022 stores approved-leave cancellation as a distinct request and decision linked to the original leave approval, retaining the approving level and all ledger entries. Approval applies compensating balance/capacity entries only for the eligible unused portion; consumed leave and assignment changes are not silently erased. Recompute affected schedules and issue alerts with idempotent event handling.
- Lead stage, project/task/document/review/leave/snag states are constrained to valid values and changed through domain services. C-017 forward lead jumps record from/to, skipped stages, reason, actor and time in immutable stage history; skipped stages are distinct from completed stages in reports. C-018 keeps a Lost lead's outcome, reason and history intact; a returning opportunity has its own Lead ID and a nullable link to the earlier Lost Lead, with permission checks on both records and reports counting each by its own period. C-019 permits reasoned, audited moves from a nonterminal lead stage to an earlier nonterminal stage; prior stage and activity records remain intact and reports retain both movements. Won conversion requirements remain. Transactional transition checks use row version/locking where concurrent updates matter.
- Revision identity is immutable: unique project/document/series/number, with file checksum and storage key immutable after finalization. Approval references exact item and revision. At most one current approved/issued revision per document (reviewed partial unique constraint or equivalent). Old revisions and transmittals remain addressable.
- Approved client evidence, issued drawings/transmittals, audit events and historical report snapshots are append-only during their retention period. C-003/C-009 set ten years from project closure for approvals and issued drawings, ten years from event time for audit, seven years after exit for employee records and ninety days from capture for site selfies. Scheduled expiry has advance Owner notice and documented holds. Corrective entries supersede originals. User-requested deletion is archive/soft-hide plus audit; controlled expiry after legal/contract review must respect holds, backup lifecycle and an audit tombstone.
- Deadline and time-log changes create dedicated history with old/new value, reason, actor and time. Personnel exit deactivates access but retains stable employee references and display snapshots in history.
- Use unique idempotency keys for offline commands, integrations, notification deliveries and outbox consumers. Offline updates carry the base record version; stale same-record writes are rejected into a conflict queue for human compare/keep/amend, while independent new evidence appends once. No last-write-wins overwrite. Store created_at/updated_at in UTC and use explicit project/employee time zones for dates and schedules.

## Transactions and migration rules

One owning service performs each business transition transactionally: state change + reason/evidence + audit + outbox. Examples: client approval of exact revision; document issue/supersession; deadline extension decision; leave approval/capacity effects; permission revocation. NAS/remote calls occur after commit through idempotent jobs with reconciliation. Never hold a DB transaction open while streaming a large file or calling an external service.

Use reviewed, versioned migrations with rollback/forward recovery notes and data preservation. Test on a restored copy before production changes. Avoid schema resets. Back up database and file metadata, verify restores and report migration status. No migration is created in Phase 2.
