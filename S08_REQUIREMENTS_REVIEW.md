### Folder intent versus NAS operations

R-017's “folder structure” and the S08 plan's “folder intent” mean template data describing the desired logical folder layout (and potentially naming conventions). They do not mean S08 creates directories, writes blobs, assigns NAS ACLs, or exposes a physical path. `FILE_STORAGE.md` says NAS is the primary physical store, metadata is separate, project creation may create versioned template folders through a retryable job, and folder failure must be visible and recoverable. Because NAS cannot participate in a PostgreSQL transaction, S08's atomicity/retry acceptance should apply to database-owned project/template structure and idempotent request identity; physical provisioning must be a separate S11-owned operation with observable status/reconciliation. No user should receive NAS credentials or unrestricted paths.

## Design questions for the persistence increment

Sol review must settle technical details below from approved requirements and conventions. Owner input is required only for material product policy absent from approved sources. The stage/milestone completion policy has now been resolved: assigned Project Lead or explicitly granted staff may complete items; required milestones block project completion; Owner or explicitly granted Team Leader may record a reasoned audited override. See S08_SPEC.md. Future-slice execution remains excluded; applied versions must remain stable. The following list records questions raised during the initial supporting review, not eight mandatory Owner approvals.

1. **Template version lifecycle:** Is a published version immutable, and how are edits, retirement/deactivation, copying, and selection of an older version handled? What version is selected by default, and can an authorized creator choose another?
2. **Existing-project updates:** After a project has applied a template, may later template edits or explicit reapplication alter its stages/milestones? If allowed, what happens to progressed/completed items and what baseline/history must remain?
3. **Template management authority:** The plan says “template management grant,” but approved sources do not name the resource/action, scope (organization/branch), eligible actors, or whether Owner-only controls exist for shared defaults. Define who may create/edit/publish/retire templates and apply them to a project.
4. **Gate policy and override authority:** R-016 says “Owner/Team Leader” may override configured gates, while current S07 lets only the Owner confirm completion before S08 gates. Which Team Leaders qualify, what explicit scoped grant/appointment is required, which gate types may be overridden, and may activation/completion/cancel gates be overridden? What reason/actor/time evidence format is required, and how is an override audited? Cancellation remains blocked by S09 regardless of this wording unless its task/access preconditions are met.
5. **Stage/milestone semantics:** Which fields make an item a stage versus a milestone; may stages be reordered, skipped, repeated, or optional; are milestone dates required, baseline dates stored, and how are actual dates recorded? R-014/R-015 give an order but do not specify these mechanics.
6. **Cross-delivery template use:** May a template support one delivery type only, or both? May template scopes differ from the immutable project baseline in S07, and if so which is authoritative? Delivery type and service scope must remain distinct (R-011/R-012).
7. **Default content activation:** R-017 lists tasks, estimates, dependencies, review/client gates, SOP links, notifications, reports and automation as possible template contents. Decide whether S08 stores forward-compatible configuration only or implements any of those behaviors; planned owning slices indicate execution is deferred.
8. **Folder provisioning lifecycle:** The sources establish retryability and recoverability but not when the app considers template application complete if NAS provisioning is pending/failed, who retries, or whether project creation can proceed. Keep this boundary explicit and resolve the user-facing lifecycle when S11 defines the NAS operation.

## Suggested acceptance and regression criteria

These are test criteria derived from the plan and source boundaries; they do not prescribe unresolved policy above.

- Seed/use a Design template and a Turnkey template; verify each preserves the exact approved default order and remains separately identifiable by delivery type.
- Create and version a template; verify an existing project's applied version remains visible and stable when a later template version is created. Reject or safely constrain mutation of a version already applied according to the resolved version lifecycle.
- Apply a template to a project and replay the same idempotency key/request: exactly one database structure is created, response identifies the same applied version, and no duplicate stages/milestones appear. Concurrent retries also yield one result.
- Inject a database failure during structure application: no partial template-derived structure is committed. Verify retry after rollback succeeds without duplicate history or audit/outbox evidence.
- Attempt application against a different project's ID, a project in another Branch, or a template outside the actor's authorized scope; backend authorization must deny it and must not disclose or mutate the other project's structure. Include identifier tampering and revoked-grant cases.
- Verify configured activation/completion gates are evaluated server-side against current project state; absent or incomplete required gates fail closed. An allowed override requires the resolved authority and nonempty reason and leaves actor/time/reason plus canonical audit evidence. Denied actors cannot override by directly calling the API.
- Ensure S08 does not mark tasks complete, create review/client decisions, issue documents, execute procurement, or claim that a physical NAS folder exists merely because template metadata was applied.
- If project creation records folder intent, simulate NAS provisioning pending/failure/retry at the S11 boundary: status is visible, retries are idempotent, and success is not falsely reported before confirmed external completion.
