# Domain event catalogue — implemented S01–S13 events and planned future families

Source: R-095 and related workflows. Business state changes and an outbox record must be written in the same PostgreSQL transaction. Event names are stable dotted past-tense facts. A worker may retry delivery, so consumers must be idempotent. Event publication is not authorization: each recipient/view/integration checks current scope before showing data.

## Envelope

event_id; event_type; schema_version; occurred_at UTC; organization_id; branch_id when relevant; aggregate_type/id/version; actor_id and safe display snapshot; correlation_id/causation_id; minimal type-specific payload. Never put credentials, full file paths, private file bodies, medical/attendance evidence or hidden AI reasoning into event payloads. Consumers use event_id plus destination to deduplicate; failures and retries are visible. Permission revocation invalidates future delivery/access even if an event was queued earlier.

## Launch notification routing baseline

The Owner's C-008 launch channels are in-app and email; mobile push, SMS and WhatsApp are later. These are technical defaults to be reviewed as each slice becomes active. Every delivery rechecks current recipient scope and skips a revoked or expired grant. In-app records remain authoritative if Brevo email is delayed or unavailable; email retry uses an idempotency key and never includes file bodies, native CAD link codes or sensitive attendance evidence.

| Trigger | Actionable recipients | Default handling |
| --- | --- | --- |
| Assignment, reassignment, deadline or review request | Current assignee/reviewer and the project manager when the action changes their work | Mandatory in-app; email for direct action requests, configurable for routine copies. A C-023 exited person is never a recipient. |
| Correction, approval and issued revision | Submitter/task owner, current reviewer or scoped project/client recipient | In-app plus email when a response or issued transmittal is required; exact revision and permission checked at delivery and view. No new delivery decision is sent during a C-024 lead-exit hold. |
| Leave decision or cancellation impact | Employee, approver, affected Team Leader and affected task owners | Mandatory in-app; email for approver/actionable impact; C-022 pending cancellation changes no capacity. |
| Project cancellation, lead-exit hold, access loss or critical site risk | Owner and affected internal managers; external recipients only through an explicitly approved notification/template | Immediate mandatory in-app and essential email for internal decision makers; critical alerts may bypass quiet hours under an Owner-configured policy. Existing portal grants are still enforced on every view. |
| Morning/evening/weekly/monthly summaries and personal reminders | User's current authorized scope | Respect preferences and quiet hours; dedupe by recipient/period/version. Summaries do not substitute for actionable alerts. |

Reminder schedules and critical thresholds are versioned Owner configuration before their respective slices run. Missing recipient, quiet-hour rule, failed email or stale grant is visible in operations status rather than silently counted as delivered. Only create events when a domain slice needs them. A source module owns its event schema. Consumers must not replicate another module's business rule; projections can be rebuilt from authoritative records.

## S08 event payloads

S08 emits template.version_created with template/version IDs, version number, name, SHA-256 definition hash and stage/milestone/folder counts; project.template_applied with applied version ID/number and structure counts; project.plan_item_completed with item ID/kind/key, project version and completion time; and project.gate_overridden with incomplete milestone IDs and project version. Each is paired with canonical audit evidence and an NTF outbox row in the same transaction. Outbox rows are durable routing primitives only; S08 sends no customer messages or scheduled notifications.

## S09 implemented task events

S09 task commands persist canonical audit evidence, a domain event and an NTF outbox delivery in the same transaction as task and history changes. Implemented event names are `task.created`, `task.assigned`, `task.started`, `task.waiting`, `task.completed`, `task.updated`, `task.stopped`, `task.closeout_approved`, and `project.cancelled`. S09 also admits `organization.employee.exited` in the database event catalogue for the exit workflow. Event payloads carry task/project identity, relevant version/state/owner evidence and reason; task creation includes applied plan-item, tags and checklist metadata where supplied. Project cancellation records the number of stopped tasks; each stopped-task event links its ProjectStatusChange ID.

The employee-exit transaction creates a mandatory in-app Owner alert. Each resulting project.on_hold event routes a mandatory in-app notice to active assigned contributors with current project access. Delivery consumers recheck current access. Project cancellation emits transactional events/outbox rows; S09 does not create a cancellation notice. S09 does not emit or execute S10 deadline/overdue events, recurring generation, client decisions, external closeout access, or reminders/escalations.

## S10A waiting events

Ordinary wait records task.waiting; explicit resume records task.started with resumedFromWaiting evidence in the linked audit snapshot. Cause, responsible party and saved state remain in immutable task history and audit. Both use the existing transactional NTF outbox entry; no configured task.waiting recipient routing or live delivery is claimed by S10A.

S10B uses `task.deadline_changed` for each controlled committed-date replacement, with old/new date and task version in canonical audit/event evidence. S10C uses `task.updated` for each dependency add/remove with edge ID, action and dependency revision. An acknowledged early start remains `task.started` and includes the exact unfinished predecessor IDs. Completing a predecessor creates a separate `task.dependency_completed` event per linked ordinary Waiting dependent B, plus an in-app notice to B's current primary owner. Its delivery predicate rechecks Waiting state, active edge, project/owner access and account state. Ordinary configured `task.waiting` recipient routing remains open.

S10D uses the S05 `approval.requested`, `approval.decided` and `approval.withdrawn` lifecycle with approval type `task.deadline_extension`. On approval, `task.deadline_changed` carries the prior/proposed committed dates, task version and extension approval ID; rejection preserves the current commitment. S10E ordinary Waiting routes `task.waiting` in-app notices only when the owner's current Team opted in; delivery rechecks the exact Waiting cycle, opt-in and current recipient access. Team setting changes use the organization team update evidence; Owner timezone changes emit `organization.settings.changed` with before/after timezone and settings version. S10F records `task.recurrence_configured`, `task.recurrence_paused`, `task.recurrence_resumed` and `task.recurrence_generated`; each schedule/occurrence event carries rule/task/date/version evidence and is paired transactionally with audit and outbox evidence. Generated occurrence creation and its linked task commit atomically.

## S13 internal review events — COMPLETE for development/local staging

S13 writes canonical audit evidence, a domain event and the associated outbox delivery in the same transaction as each review command. Event names include `review.category_changed`, `review.assigned`, `review.requested`, `review.started`, `review.commented`, `review.approved`, `review.correction_requested`, `review.correction_assigned`, `review.escalated` and `review.withdrawn`. Payloads identify the organization/project/task/round/submission and, for drawing work, the exact drawing/revision/blob/checksum; category/severity and annotation count are included where applicable. Payloads never contain markup bytes or private storage keys.

Escalation creates a mandatory generic in-app notice for the active Project Lead or Owner fallback. The alert does not reveal drawing details; the recipient must pass current access checks to open review details. Category edits, priority/deadline changes, correction ownership and exit recovery retain reasoned audit/domain evidence. Failed authorization or transaction rollback creates no partial review state or notification. S13 does not claim configured email, broad S24 escalation policy or client-facing alerts. S13 is COMPLETE for development/local staging; see S13_COMPLETION_REPORT.md for acceptance evidence and limits.
