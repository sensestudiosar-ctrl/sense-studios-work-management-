Status: COMPLETE for Owner-authorized development/local staging, 2026-10-05. Final gates and independent Sol acceptance are recorded in S24_COMPLETION_REPORT.md and S24_ACCEPTANCE_REVIEW.md.

All routes require a current internal cookie session; Owner requests also retain the accepted Owner-readiness check. Responses are `Cache-Control: no-store`. POST requests require the configured exact Origin and `x-csrf-token`. UUID route identifiers and strict body schemas are validated. Client dashboards use the existing isolated client portal routes, never these internal routes.

Each value stays a primitive cell with explicit nested field labels; operational bodies are not emitted as a giant JSON cell. Dates filter dated rows. Undated current plans/state and accepted snapshots remain identifiable by their retained field/period data. The report is not a new historical reconstruction of operational state before its generation time.

R-060 morning/evening summaries retain today's due/priority/review/waiting work, actual completion history, outstanding work, actual logged seconds, current issues and tomorrow targets. Weekly uses the trailing seven local calendar days; monthly uses month-start through the generation day. Their accepted health/performance snapshots must fit that period; empty accepted performance is explicit unavailable. Period workload/leave and time use their actual owning sources. The immutable summary envelope retains kind, from/to, generation time, every section and complete source manifest.

R-058/R-059 schedules have explicit TASK_REMINDER, SUMMARY and EVENT_NOTICE kinds. Weekly requires configured weekdays and monthly requires configured dayOfMonth; invalid/nonexistent monthly calendar days do not invent an alternate date. Task rules require explicit offset and may filter current priority/project; completed, cancellation-Stopped and reassignment-blocked work is excluded. EVENT_NOTICE accepts only catalogue events with supported owning source mappings, excludes recursive dashboard/report events, and filters current source scope/project/priority. Audience SELF/OWNER/EMPLOYEE/MANAGER retains current source visibility. Critical/mandatory flags use accepted S04 preferences/quiet-hours/verified-address rules. Positive overdue offsets repeat on eligible local days after the threshold; zero/negative offsets match their exact day.

Kind-specific fields are validated rather than silently ignored: summaryKind belongs to SUMMARY, offsetDays to TASK_REMINDER and eventNames to EVENT_NOTICE. SUMMARY covers the recipient's full current scope and rejects task/event priority/project filters. The UI hides those irrelevant inputs and clears kind-specific state when switching kinds. Optional weekday/month-day cadence gates remain supported for each kind.

Stable generated slots are source rule + recipient + local day/task or canonical event ID, independent of rule version. Editing a rule invalidates prior pending delivery through its recorded version but never regenerates the same recipient/event or day/task slot. A new recipient can receive their first authorized slot. Personal reminders use a single creator slot. Concurrent workers/restarts and repeated DST clock hours deduplicate through the persisted unique constraint/advisory lock.

Command advisory locks precede identity/session locks, so revocation during a wait is observed before any write. Current identity, session, employee/reporting-team, role grants/overrides and source task/project/assignments are locked through the transaction. Scoped public service reads reuse that transaction. In-app scheduled delivery reuses the notification delivery transaction for its current source check and final write. Notification titles/bodies contain no confidential task/report text; authenticated dashboard/history displays current-authorized evidence. External email retains the existing provider at-least-once boundary and generic text.
