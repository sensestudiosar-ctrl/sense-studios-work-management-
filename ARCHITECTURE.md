## Stack choices and tradeoffs

| Choice | Why | Alternatives and tradeoff |
| --- | --- | --- |
| TypeScript, current supported Node LTS, pnpm workspace | One typed language across web, API and worker; broad hiring/AI knowledge and tooling. Pin versions at implementation. | Python/Django is mature but splits web/backend languages; full-stack Next.js shortens deployment but places complex domain/background work near UI conventions. |
| React + Vite responsive PWA | Mature component ecosystem, fast local build, separate API contract, suitable for internal dashboards and portals without SEO dependence. | Next.js adds SSR/server actions that these workflows do not currently need; Vue is viable but reduces shared team conventions. |
| NestJS modular REST API, OpenAPI contract | Explicit module boundaries, guards, validation, dependency injection and generated API documentation suit broad workflows. | Express/Fastify alone needs more local conventions; microservices add deployment and data-consistency cost. |
| PostgreSQL | Relational constraints, transactions, JSON where justified, indexes and mature backup support for approvals, revisions, scopes and audit. | SQLite is simpler but weakens concurrent multi-user/server workflows; document stores make core relationships harder to enforce. |
| Prisma ORM with reviewed SQL migrations | Productive typed CRUD and broad documentation. Use reviewed SQL for constraints/features Prisma does not express; never use schema push on production data. Pin a vetted version after approval. | Kysely/SQL gives more direct control but requires more handwritten mapping; TypeORM has broad support but weaker migration discipline. |
| Jest (API/domain), Vitest + Testing Library (web), Playwright (E2E) | Layered fast tests plus real browser/device coverage. | One runner for everything is simpler but does not replace browser and DB behavior. |
| Docker Compose on the existing MINISFORUM NAS if capacity/security tests pass | Lowest recurring hosting cost; one operational unit for web/API, PostgreSQL and worker, with NAS file access local. The reported 8 GB RAM makes memory limits and load tests mandatory. | Small separate host becomes fallback if NAS compute/container isolation is inadequate; managed hosting adds recurring cost and private NAS connectivity work. |

These are recommendations, not installed dependencies or an approved stack. Vendor/version support, NAS model, the selected Tunnel deployment and restore procedures must be verified before production deployment.

## System and dependency direction

One repository, modular monolith, one PostgreSQL database. A static web/PWA client calls a versioned JSON REST API. Nest modules own writes and publish domain events through a transactional outbox. A worker in the same codebase handles notification delivery, reminders, reports, NAS reconciliation and external sync. An HTTPS reverse proxy is the only public entry point. External portals use the same API with narrower resources and authorization.

UI → API controller/validation → authentication/session → authorization policy → owning domain service → transaction/repository → PostgreSQL; committed outbox → worker → notification/integration/read projection. Cross-module calls use explicit module services or events. No controller, UI, worker or AI path may bypass domain rules or policy checks.

## Core boundaries

- Frontend owns presentation, navigation, form UX, loading/empty/error states, and offline local queue. Backend owns business validation, transitions, permissions, scoring, audit, and writes.
- S08 adds organization-scoped versioned project templates and project-owned plan snapshots. Template grants do not confer project access. Project creation applies the selected version atomically with S07 project/baseline evidence; later template versions do not rewrite existing projects. Folder/naming definitions are intent only until S11. Project completion checks required milestones; Owner or explicitly granted staff override records reasoned audit evidence without bypassing other access or approval rules.
- The CRM transition service enforces C-017: a scoped actor with a lead-stage-change grant may jump forward with a required reason; it records from/to, skipped stages, actor and time in one transaction and reports skipped stages separately from completed stages. Lost reason and Won conversion checks still apply. C-018 keeps Lost leads final: a returning enquiry creates a new lead linked to the earlier one, with fresh stage history and no rewrite of the earlier loss. The link is visible only where the actor may view both records. C-019 permits a scoped actor to move a nonterminal lead back to an earlier nonterminal stage with a required reason; the prior stage event remains intact and reports show the return without fabricating or undoing activities. Won/Lost records are not reopened by this rule.
- API contracts are generated from the backend OpenAPI document into a typed web client. All external inputs get server validation; version breaking changes.
- Each request carries authenticated actor, organization, branch scope, project membership and session identity. Default deny; an Owner has full organizational authority, with Owner-only authority for cross-branch project grants under C-002. Use server-side revocable sessions, secure HttpOnly/SameSite cookies, CSRF protection for cookie-authenticated writes, rate limits, safe headers/CSP and server upload validation. Owner and employees use passkeys; invited clients/consultants use emailed one-time codes for portal viewing. Formal client approval requires a registered passkey step-up. Lost employee passkeys require Owner-verified recovery and revocation; the Owner keeps a second passkey and offline recovery code. Do not treat an email code as sufficient identity proof for a formal client approval.
- Job role, employee reporting relation within the Branch/Team structure, and permission grant are separate. Resource policies combine grants with branch/team/project scope and conditions. Hidden controls improve UX only.
- A permission change or forced logout must invalidate effective future access immediately: protected requests recheck server-side session/grant state rather than relying on long-lived self-contained tokens.
- A shared approval engine stores request type/resource, requester, approver/level, status, reason, evidence, expiration, delegation and audit. Type-specific policy validates the decision and applies the owning domain command. Project cancellation is Owner-only under C-010; a Project Lead/Team Leader request does not itself change project state. C-011 requires the project cancellation and all unfinished delivery-task stop transitions, reason/evidence, audit and outbox events to commit atomically. The cancellation command remains unavailable until S09 provides the task transition, although S07 prepares the project lifecycle boundary. Completed tasks remain completed; later closeout tasks are explicitly typed and linked without reopening delivery. C-016 uses type-specific approval checks: assigned Project Lead or explicitly granted Team Leader, required reason/scope/owner/due date and audit. A separate expiring, item/work-package-scoped vendor/consultant grant may be approved for that closeout task; native CAD links and cross-branch employee grants remain Owner-only. Under C-012, cancellation first inventories active native CAD links, requires Owner revocation in MinisCloud and records confirmation; only then may the database transaction finalize project cancellation, task stops and vendor/consultant app-access revocation. The same committed transition applies C-013 client read-only issued-record scope, requires an Owner-set C-015 end date for each retained client project-access grant before final cancellation, and withdraws pending client decisions while preserving evidence. Subsequent reads enforce expiry at request time; an Owner-approved extension is separately audited. No shared duration is configured; each client grant's end date is checked independently. A pending cancellation request is not a Cancelled project. Do not assume a MinisCloud automation interface; reconcile and surface failed or unconfirmed revocations. A management decision queue projects pending requests; it does not become a second source of business truth.
- Site snag policy applies C-020: the assigned Project Lead or an explicitly authorized Team Leader names a project-scoped verifier who did not perform the repair. Verification checks current assignment, project access and evidence; a failed check returns the snag to In Progress while retaining the attempt. C-021 reserves the separate Verified-to-Closed transition to the assigned Project Lead or explicitly authorized Team Leader, with a current passed verification and a distinct recorded close action. The closer may also be the named verifier if they hold both authorities; the separate management decision remains explicit.
- C-023 makes employee exit revoke sessions and grants immediately, place each unfinished task in Waiting with a needs-reassignment reason while retaining its previous state and historical primary owner, and create a manager-visible handover queue. S03 supplies immediate suspension/revocation, but the full employee-exit command is enabled only after S07 project holds and S09 task waits can commit with the exit; this prevents partial handover behavior during the build. A scoped human manager selects the replacement before work resumes; history is append-only and reviews/gates are rechecked. C-024 atomically moves any Active project led by the departing employee to On Hold with reason, removes current-lead authority while preserving leadership history, pauses new delivery decisions and alerts the Owner. After the Owner appoints an eligible replacement, ordinary gate checks permit an audited On Hold-to-Active resume.
- C-022 treats cancellation of approved leave as a new approval request routed to the same approval level as the original decision. Only an approved cancellation reverses future leave balance/capacity effects; the original approval, any used leave and every reassignment remain historical. Recompute affected schedules and notify managers and task owners without silently undoing assignments.
- Important mutations write before/after, actor ID/snapshot, reason where required, and business event in the same DB transaction. Audit is append-only during the C-003 retention period; corrections create new entries. Controlled expiry requires legal/contract review, holds and backup handling.
- Notifications consume outbox events, use current-recipient policy checks, idempotency/dedupe keys and persisted delivery attempts. EVENT_CATALOGUE.md sets launch routing defaults, quiet-hour handling, external-message approval and failure visibility; actionable in-app records remain available when email delivery fails. Scheduled jobs use the same durable job/outbox mechanism. Redis/BullMQ is a later scaling option, not initial infrastructure.
- Realtime status is a convenience stream (SSE or polling) over persisted notifications/decision views. Launch alerts use in-app and email through the approved Brevo free plan, subject to quota/delivery tests; SMS/WhatsApp and web push are later options. In-app records remain the source of truth if email is delayed.
- NAS operations cannot participate in a PostgreSQL transaction. File upload uses staged object, validation/checksum, metadata finalization and reconciliation. No browser receives NAS credentials or raw paths. See FILE_STORAGE.md.
- Offline site work is phased: cache app shell, store explicitly supported drafts/commands in IndexedDB with stable local IDs, base record versions and idempotency keys; sync on reconnect. Independent new observations/photos append once. A same-record version conflict stops that command and shows server and local values; the user keeps the server version or submits a reasoned amended new version after reviewing both. No automatic last-write-wins, silent overwrite or guaranteed background sync. Do not cache confidential project files by default.
- Integration adapters own accounting, calendar, website, maps and future API/webhooks. Retries are idempotent; failures appear in operations status. AI is a later read/recommendation adapter over already authorized context; human decisions pass through ordinary domain APIs.
- Error responses carry stable codes and safe messages; server logs include request/correlation ID and relevant entity IDs without secrets, file paths or sensitive payloads. Health, failed jobs, storage reconciliation and backup checks are observable.

## Cost-aware deployment and recovery proposal

The owner reports a MINISFORUM NAS with 8 GB RAM, MinisCloud OS and an existing domain. MINISFORUM's N5 Air documentation lists Docker support; exact model is still being confirmed. Recommend a single NAS-hosted deployment with constrained web/API, PostgreSQL and worker containers only after memory, storage, upload and restore tests pass; do not run local AI on this baseline. Use least-privilege volumes/accounts. The owner selected a Cloudflare Tunnel as low-cost public HTTPS ingress: it avoids inbound router exposure, but Cloudflare carries traffic and its Free plan limits each proxied upload request to 100 MB, so app uploads require resumable chunks and realistic testing. Cloudflare also flags serving video and other large files through public Tunnel routes under its service-specific terms; test a separate NAS-sharing path for vendor CAD. Never expose NAS administration, SMB/NFS or PostgreSQL to the internet. If NAS capacity or OS isolation fails validation, move app/database to a small local server and keep NAS file storage/backup. The owner selected Cloudflare Tunnel for public app ingress (C-002 Q3); the architecture was approved at checkpoint 2e46805; NAS and production deployment validation remain pending. Vendor and assigned consultant CAD delivery uses Owner-issued, file-specific native MinisCloud links with seven-day expiry, extraction code, app audit record and immediate Owner cancellation when access ends (C-006). Client files remain PDFs/images only.

Schedule nightly encrypted, consistent database-and-file backups to the Owner's always-reachable offsite computer/NAS and monitor success. The accepted target is at most one day of data loss after total primary-NAS loss. Keep NAS snapshots for local rollback, test restoring database plus an approved file revision together, and document offsite connection/key custody. Separate staging from production before live data.

## S09 tasks, participants and state (implemented)

The S09 task service persists an organization-bound task with one active primary owner, optional project and applied-plan item, type, priority, target and optional start date/effort, explicit review requirement, tags/checklist metadata, version and status. Collaborators are distinct from the primary owner and have optional explicit estimated hours. Task owner/status change records and closeout approval evidence are persisted separately. Project tasks are visible only with current project access; assignment alone does not grant project management authority. S09 currently permits only NOT_STARTED → IN_PROGRESS → COMPLETED through the ordinary task transition command, and completion fails closed whenever review is required. Review states remain reserved for S13/S14 handlers. See the S09 sections in DOMAIN_MODEL.md, DATABASE.md, PERMISSIONS.md, WORKFLOWS.md and EVENT_CATALOGUE.md.

## S10A ordinary Waiting/resume

TaskService now owns explicit ordinary wait/resume commands. Only the active primary owner or Owner may move IN_PROGRESS to WAITING or restore saved IN_PROGRESS; current task/project access, closeout approval and optimistic versions are rechecked. Task state, reason, delay cause, optional descriptive responsible party, immutable history and canonical audit/event/outbox commit in one transaction. Ordinary wait differs from mandatory C-023 reassignment waiting; the latter cannot use ordinary resume. S10B added separately controlled committed dates. S10C added project-local dependency graph commands, explicit early-start evidence and delivery-time-rechecked completion notices. Employee extension decisions, configured ordinary Waiting notices and recurrence generation remain pending S10 work. See S10_SPEC.md and S10_PROGRESS_REPORT.md.

## S12 document revision architecture — COMPLETE for development/local staging

The DOC boundary owns project drawing records, append-only revisions, approval-evidence bindings, current/superseded selection, exact issue/transmittal records and named internal acknowledgements. It uses S11 document authorization and immutable NAS blobs rather than exposing storage paths. Number allocation and current-selection changes serialize on the drawing; expected versions reject stale UI commands. Revision and issue records carry composite project/organization identity and canonical event evidence enforced by PostgreSQL guards.

S13/S14 remain the only producers of internal/client approval facts through the private DOC module port. There is no generic public state or approval endpoint. The public issue route fails closed until the exact downstream facts exist, and rechecks each recipient's access to each file. Project completion/cancellation status evidence anchors the ten-year issue-retention clock. S12 migration preservation, integrated runtime and local-staging acceptance passed; see S12_COMPLETION_REPORT.md for evidence and production limits. S13 and later remain unauthorized.
