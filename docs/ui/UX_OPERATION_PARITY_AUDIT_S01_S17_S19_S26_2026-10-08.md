## Method and evidence limits

The expected action names below come from [the feature coverage inventory](UX_VALIDATION_FEATURE_COVERAGE_2026-10-07.md#workflowaction-family-register). Current homes and API families come from [the parity ledger](UX_OPERATION_PARITY_LEDGER_2026-10-08.md). Slice reports/specifications/contracts and current web/API sources are linked per row. A listed controller or contract is a trace point, not proof that every UI control invokes the matching command. Where I did not verify the exact control-to-request binding, JSON schema, effective capability predicate, resulting persisted state, or recovery behavior, the field is explicitly **unverified**. No actions are inferred from prototype-only representation.

## Ambiguities and disposition

- No operation-by-operation UI control to exact HTTP body crosswalk was established for the listed S01–S17 or S19–S26 families. The contract/controller pointers above make the gap reviewable; they do not close it.
- The source inventory and accepted reports settle the boundaries for S05 typed decisions, S07 cancellation/closeout, S14 client roles, S17 leave cancellation and excluded attendance operations, S19 separate approval stages, and S26 human finalization. If a current control presents a different combined or automatic workflow, treat that as a requirement conflict and ask the Owner; this audit does not choose a rule.
- Current S18/S27 audit is separate and explicitly bounded. Its existence does not establish parity for the rest of the product.
- S18/S27 local acceptance, S19–S26 development/local-staging completion, and all other status claims remain bounded as recorded by current owner direction. Actual-project R-104/R-105 and production readiness are unverified; this audit makes no claim about either.

No application code, status document, requirement, or existing ledger was changed. No tests or product gates were run. Required documentation check: `git diff --check`.
