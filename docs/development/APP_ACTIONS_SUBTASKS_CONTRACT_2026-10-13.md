## Actionable read boundary

Keep task, assigned-review and decidable-approval sources separately typed and counted. D2 requires one complete server-composed attention queue; independently paginated frontend sections are superseded. E1 evaluates eligibility, authorization, rows and counts in one RepeatableRead snapshot with one readAt clock and organization calendar, before a single global sort/page. Existing personal task counts remain personal counts; review obligations do not become owned tasks. D3 task-only predicates visibly select Tasks; clearing them restores all source types while retaining shared search/project predicates. An included-source failure withholds the complete page/count instead of publishing partial fresh results.

Add domain-owned read ports, with actor and transaction arguments, returning authorized projected rows and exact totals after eligibility filtering. The same evaluator supplies page rows and count. Use stable source IDs; task IDs deduplicate within task source, review rounds use round IDs, decisions use request IDs. Return source, sourceId, taskId where real, title, project identity where authorized, responsibility, typed reason, applicable deadline, existing action destination and source read timestamp. Do not disclose inaccessible child/task/evidence identifiers. Failures/denials remain source-specific; no aggregate completeness claim when a source is unavailable.

Task eligibility reuses TaskService activeActor/taskAccess/project state/closeout/reassignment checks and existing command capabilities. Target compared with the organization calendar provides due-today/overdue reasons only when the actor has an actual current task command. Returned corrections can provide a current work reason without being overdue. Ordinary In Progress or collaborator membership is insufficient. A collaborator currently cannot progress a task merely by collaborating: TaskService.transition requires Owner or primary owner. Include a collaborator only for a separately established current authorized action; do not broaden transition permissions. Waiting must have a real resumable action belonging to that actor; do not infer responsibility from waitingResponsibleParty free text or unfinished dependency notifications. Managers see reassignment only through existing reassign capability and requiresReassignment, not all team overdue tasks. Unsupported risk/follow-up/severity remains absent.

Assigned reviews use ReviewService's named current reviewer and exact round/submission/project/independence/revision-access guards (inbox personal/mine and its domain evaluator). Keep review dueDate's current Committed-to-Target semantics. Do not infer a reviewer obligation from the task's generic review-phase filter. Preserve round ID in navigation/action.

Approvals cannot reuse ApprovalService.attention as proof of decidability: attention checks handler.canView only. Extract the existing read-only eligibility rules from decide into a shared transaction-aware function: active actor, current pending request, unexpired request, registered handler, current delegated identity/expiry, handler.canDecide and handler.canSelfApprove/requester rule. Reuse that evaluator in decide and new projection; request-time command authorization remains authoritative. No automatic decision or domain-state mutation. Use request/type IDs and existing domain decision destination; do not invent a task link from sourceId unless the owning handler explicitly supplies an authorized canonical task link. Preserve the S26 handler's explicit canSelfApprove exception instead of globally banning all author review.

Use existing source-owned read transactions. Never return a total from a capped scan as exhaustive. Approval attention's existing 5000 scan cap and cursor are not an exact decidable total. For the new complete source, count all evaluated current candidates, or explicitly return unavailable/incomplete with no total if a bounded safety limit is necessary. Do not hide this as zero. Stable ordering starts with actual applicable deadline, existing priority only where meaningful, and source ID tie-breaker; no invented severity thresholds.

Suggested bounded implementation groups: task projection in TaskService/controller and tests; review projection in ReviewService/controller and tests; approval evaluator/projection in ApprovalService/controller and tests; frontend adapter using these complete source envelopes. Keep domain writes in owning services. Source authorization and aggregate semantics require Sol review before accepting Luna implementation.

## Genuine one-level child tasks

Use the additive organization-scoped TaskSubtaskLink relation in migration118, preserving existing Task columns and rows. Its parent/child constraints and database triggers implement the same approved immutable one-level relationship. The earlier parentTaskId column proposal is superseded by this reviewed source representation; no deployed migration is edited. Do not assume retained preview115 equals the source directory count.

Add a separate POST /tasks/:parentId/subtasks using the canonical create fields plus expectedParentVersion. Parent ID comes from the route; child project is the parent's actual non-null project and must match any explicitly provided project. Parent access and normal create/eligible-owner/collaborator/assignment/review/capacity guards all apply. Ordinary staff may self-create only under current rules; manager assignment retains current explicit authority. Parent access never grants child access, nor does child membership grant parent access. Relationship is immutable in this bounded slice: no reparent/detach, no automatic cascade of owner/date/status/review, and no new deletion/archive command.

Parent must be a top-level task, nonterminal, not reassignment-blocked, and eligible for ordinary task editing/new project work under existing lifecycle guards. Do not add children after a parent has entered a review-protected state or after completion/cancellation. Children cannot themselves have children. Reuse existing createInTransaction to persist a real child and its ordinary audit/event/history; record parentTaskId in the child-created evidence and a versioned reasoned parent task.updated event. The parent version changes when its child set changes, preventing stale parent forms from silently proceeding. No independent new task type or fake subtask status.

Serialize child creation and parent completion with the parent task row lock. Validate expectedParentVersion before insertion. SQL guards must enforce same organization/non-null same project, no self-link/second level, immutable relation and eligible parent. A parent transition to COMPLETED is rejected whenever any child status differs from COMPLETED; cancelled/stopped children do not satisfy the Owner's every-child-completed rule. Existing project cancellation remains able to stop parent and children through its ordinary workflow; this does not count as completion. Existing project archive/review rules remain unchanged.

Completion is not confined to TaskService.transition. Enforce the guard through a shared transaction helper called by TaskService.transition, ReviewService.complete and ClientReviewService.complete, plus a database completion trigger covering every task status write. Preserve existing review evidence validation, task version increments, status history, timer pauses and events. Parent row locks serialize against concurrent child insertion; SQL completion guard must inspect the full child set, including inaccessible children, without returning their identities. Return a generic completion blocker; detail projection shows only independently authorized child summaries. Any count of hidden children must follow an explicitly reviewed disclosure contract; the initial projection can use a generic blocked flag instead.

FK RESTRICT prevents parent deletion while children exist. Retain existing task immutability/delete policies; no delete endpoint is added. Review/correction links, dependencies and recurrence remain their own relationships. A recurrence-generated task does not inherit children merely because its source is a parent; automatic child copying is not part of this contract.

## Adopted source representation — 2026-10-13

The implementation replaces the proposed nullable Task.parentTaskId with an immutable TaskSubtaskLink table. This is a source design refinement of the approved product rule: it prevents raw Task responses from exposing inaccessible parent IDs. Existing Task scalar rows remain unchanged. GET /tasks/:id/subtasks explicitly authorizes each child and optional parent; it returns only visible items, generic completionBlocked, isSubtask, canCreate and taskVersion. List responses batch-query links for already authorized page IDs and add only isSubtask:true. No hidden child total or parent ID is supplied.

POST /tasks/:parentId/subtasks accepts canonical create fields plus expectedParentVersion. Parent Owner/primary-owner or existing explicit project.manage+task.assign management authority is required; collaborator visibility alone cannot change the child set or block another user's completion. Child assignment/access remains the canonical create workflow. Same-project graph advisory lock precedes task row locks. The forward migration's immutable scoped links require canonical child-created and parent-updated audit/domain evidence; all completion paths use the shared guard.

The graph evaluator combines active explicit dependent-to-predecessor edges with implicit parent-to-child completion edges. Both link and dependency inserts take the existing project graph lock, and both SQL and API prevent direct/indirect cycles. This preserves valid sibling dependencies without allowing completion deadlocks. New source-only tests cover strict controller/CSRF/version handling (15/15 HTTP boundary suite passed with DATABASE_URL unset); prepared PostgreSQL cases cover independent child workflow/date/marker, parent gating and explicit/implicit cycle rejection. Those database cases have not run. Internal/client completion, graph races, migration preservation and SQL evidence require real dedicated-target acceptance before COMPLETE.
