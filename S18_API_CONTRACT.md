# S18 Skills, SOP, knowledge and training API contract

Owner authorized S18 on 2026-10-03. C-025–C-027 settle audience/private storage, named-reviewer completion and independent publication. This is the accepted S18 API handoff, not current-tree acceptance evidence; current integration acceptance is recorded separately after the combined S18/S27 gates pass.

## Skill boundary — R-044.a–d, R-045.a–b

SkillsService owns SkillCatalogue, SkillRating, immutable SkillRatingChange and SkillChangeRequest, and SkillReceipt. SkillLevel is BEGINNER, INTERMEDIATE, ADVANCED or EXPERT. There is no numeric score or automatic promotion. No catalogue entries are silently seeded from source examples.

Use existing ProjectActor including a live sessionId supplied by the controller. Every command locks/rechecks active account, current session, organization and active employee state. Own profile/request access is implicit for active staff. Management access requires Owner or an active reporting ancestor within the target's current home Branch and Team, plus explicit skills.view and skills.manage TEAM grants. A title, project assignment or cross-branch project permission never grants employee-skill authority. Recheck target and approver on decisions; employee exit denies future commands and preserves history.

GET /api/v1/skills/setup returns skills, visible employees and eligible approvers; no inaccessible names or identities. GET /api/v1/skills/employees/:employeeId returns current ratings, immutable changes and requests with current capabilities. Active employees see their own profile; scoped managers see their current reports; Owner sees the organization.

POST /api/v1/skills/catalogue accepts {commandId,name,reason}. Owner only; normalize trimmed names consistently and enforce organization-wide uniqueness. Returns catalogue record. Creation is audited, without inventing employee ratings.

POST /api/v1/skills/requests accepts {commandId,employeeId,skillId?,proposedSkillName?,requestedLevel,expectedRatingVersion,approverAccountId,reason,trainingSourceId?}. Exactly one of skillId/proposedSkillName is required. expectedRatingVersion is zero for no official rating, otherwise the exact current version. Own employees may request; scoped management may recommend for reports. An employee's request cannot change the catalogue or official rating. Bind a named currently eligible manager/Owner to shared approval type skill.change. Reject duplicate pending employee/skill requests and ambiguous normalized proposed names. A completed training source may be bound only after the Training integration exists; initially non-null trainingSourceId fails closed.

POST /api/v1/skills/requests/:requestId/decision accepts {commandId,outcome:APPROVED|REJECTED,reason}. Only the named eligible current approver decides; delegated decisions are disabled. Self-request approval is denied. The shared ApprovalService stores exact immutable decision evidence. Approval atomically creates a proposed catalogue entry if needed and applies the exact requested rating, provided expectedRatingVersion is still current. Rejection never changes the catalogue or rating. A stale request must not overwrite intervening official history. Initial approved rating is version one with null fromLevel; subsequent changes increment exactly once.

POST /api/v1/skills/ratings accepts {commandId,employeeId,skillId,level,expectedRatingVersion,reason}. Owner-only direct official control, retaining the same history/event/version guarantees. Scoped managers use the reasoned recommendation/approval path. Training completion never calls this command or approves a request.

Owner catalogue/direct-rating exclusivity does not prohibit Owner recommendations: the Owner may submit a skill-change recommendation for an employee to a different currently eligible scoped manager. Such a request follows shared approval and cannot be self-approved. Where no distinct eligible manager exists, Owner direct official control remains available.

All writes use strict DTO validation, UUID IDs, 3–1000 character reasons, named enum values and 1–120 character catalogue names. commandId is actor-scoped replay protection: exact retry returns the original result; changed payload conflicts. Rating changes serialize employee/skill and bind immutable version/evidence. Catalogue, change/request/receipt rows are append-only; runtime cannot delete history. Creation/change/request/decision + audit/domain/outbox are atomic. Skill event names are skill.catalogue_created, skill.change_requested and skill.rating_changed. They must be registered in the code and SQL catalogues with matching subjects. Notification delivery must not reveal profiles to revoked or unrelated principals.

## Exact publication — R-055.b/R-056.b, C-027

POST /api/v1/library/:recordId/publication-requests accepts {commandId,versionId,approverAccountId,reason}. Exact immutable SOP/KNOWLEDGE version only, current author authority and audience access; no MODULE approval requests. Register S05 type library.publish with sourceType library_version/sourceId version.id/sourceGeneration version.version. Named publisher must have current library.manage and library.view in selected audience; non-Owner submissions cannot name their author/requester. POST /api/v1/library/publication-requests/:requestId/decision accepts {commandId,outcome,reason}. Named current eligible publisher only; no delegated or self approval. Approval creates immutable LibraryPublication and atomically selects that exact version only if no newer published version exists. Rejection leaves published pointer unchanged. Owner POST /api/v1/library/:recordId/publish accepts {commandId,versionId,reason} and directly publishes with the same exact history/event guard. Owner cannot rewrite authored content or bypass current-pointer ordering. For organization library author/publication authority, staff need explicit library.manage/view ORGANIZATION grants; Team grants and job titles do not grant it. This permission does not grant other-Team employee/project/file access.

library.publish_requested event subjectType library_version subjectId version.id after {approvalRequestId,recordId,versionId}; shared ApprovalRequest.context exact {recordId,versionId,approverAccountId}, reason matches. LibraryPublication existing library.published payload binds approvalRequestId or null Owner direct. A non-null request must bind exact approved canonical decision, current decider and immutable version author independence. MODULE activation may retain null approval under current scoped training management, distinct from SOP/knowledge publication.

## Training — R-057.a–c/R-045.a–b, C-026

TrainingService/Controller owns TrainingAssignment/Change/Attempt; shared LearningReceipt is actor-scoped replay. POST /api/v1/training/assignments {commandId,employeeId,moduleVersionId,reviewerAccountId,reason,recommendationReason?,practicalTaskId?} requires Owner or current same-Branch/Team reporting manager with training.manage and training.view TEAM grants. Assignment and selected reviewer must be active; reviewer differs from trainee and has current scoped training.manage/view for target. At assignment creation, the exact MODULE version must be the latest activated version and currently accessible to trainee and manager. Existing assignments retain their exact previously activated version after later activation; every request still checks current audience/access and publication existence. Recheck contained exact SOP/file audience eligibility, including retained historical SOP publications, so assignment never confers private library access. practicalTaskId is optional existing TaskType.TRAINING_PRACTICAL with trainee primary owner/current authority; retain exact id, no automatic task creation. Exact moduleVersionId and reviewer remain immutable; replacement reviewer requires a separate future policy rather than silent reassignment.

Authored MODULE content includes existing blocks plus assessment {criteria:string,quiz?:[{id,prompt,options:[{id,label}],correctOptionIds:[id]}],minimumCorrect?:number,practicalRequired:boolean}. If quiz present, explicit minimumCorrect integer0..question count is mandatory; no invented threshold. Hide correctOptionIds from trainee/read-only library DTOs; author/managing reviewer alone can read answers. Content schema bounded and strict; named question/option IDs unique, correct choices valid. Assignment freezes exact module version/criteria/SOP links and retains data {criteria,practicalTaskId,recommendationReason}; don't duplicate answer keys in audit/employee responses.

GET /api/v1/training/setup and assignments returns own assignments and current management reporting scope only, eligible reviewers/modules/practical tasks filtered by live access. GET /api/v1/training/assignments/:id returns exact assigned module content without answers, immutable submission/review/effectiveness history, capabilities and state.

POST /api/v1/training/assignments/:id/submissions {commandId,expectedVersion,answers?:[{questionId,optionIds}],practicalTaskId?,note,reason} is trainee-only, current ASSIGNED/CHANGES_REQUIRED, active exact module/files access. Append immutable SUBMISSION attempt sequence, calculate quiz against authored criteria without exposing keys, bind practical task evidence if required, move SUBMITTED/version+1 with exact state history/audit. No automatic completion or SkillRating mutation.

POST /api/v1/training/assignments/:id/assessments {commandId,expectedVersion,outcome:PASSED|CHANGES_REQUIRED,observation,reason} is named currently eligible reviewer only, SUBMITTED. PASSED requires authored quiz threshold satisfied and required practical evidence; reviewer explicitly attests authored criteria with preserved observation. Move COMPLETED or CHANGES_REQUIRED/version+1 and append immutable ASSESSMENT attempt. Concurrent/stale attempts conflict. COMPLETED is retained; no resubmission overwrites it.

POST /api/v1/training/assignments/:id/effectiveness {commandId,date,observation,practicalTaskId?,reason} requires named current reviewer/scoped management, COMPLETED; date must valid past/current organization date. Append dated EFFECTIVENESS observations over time, never recalculate a numeric performance score.

Separate training-source upgrade request uses existing POST /skills/requests with trainingSourceId exact completed assignment and same employee; current skill version, named independent eligible approver and official level still explicitly requested. Enable this validated binding only after TrainingService integration; completion itself never creates an approved SkillRating. UI labels recommendation pending/approved distinctly from training completion.

Training changed canonical event subject training_assignment/id after {version,state,data}; change row reason matches. Training attempt_recorded subject training_assignment/id after {attemptId,kind,sequence,payload}; exact payload matches immutable attempt; no raw quiz answer-key audit. Assignments/version/attempts and receipts commit atomically with audit/domain/outbox. LibraryVersion.content may store answer keys privately; safe DTO transformation is mandatory. Strict live session/resource checks precede receipt replay and are sampled after any lock/I/O wait.

## Settled private library boundary — R-055.a–d, R-056.a–b, R-057.a

LibraryService owns LibraryRecord/Version/Publication/File/Acknowledgement/Reference and LearningReceipt. A record fixes kind SOP, KNOWLEDGE or MODULE and audience ORGANIZATION, BRANCH or TEAM at creation. Organization audiences have no branch/team; Branch has its own branch only; Team has its own branch/team. References never grant audience access. Owner chooses any audience; explicitly granted library.manage staff may manage their own current Branch/Team audience within their grant and reporting scope. A staff organization-audience suggestion may be submitted for Owner review but cannot be published by a Team-only manager. Current active audience membership and library.view grants authorize published reads; own authors and eligible managers may read unpublished material. Clients and external actors have no library authority. Old published versions retain exact identity; a new draft does not replace published content until approved publication. Assignment/acknowledgement/reference never silently selects a later SOP.

GET /api/v1/library/setup returns filtered audiences/capabilities. GET /api/v1/library?kind=... returns accessible published records plus own drafts and management drafts; optional plain text search is filtered locally/backend by title/category/text, with no AI/natural-language feature claim. GET /api/v1/library/:id returns accessible exact versions/publications/acknowledgement status and file metadata, excluding storage keys and assessment answer keys. Unknown/inaccessible IDs fail closed. Lists never expose other audience titles, employees or counts.

POST /api/v1/library accepts {commandId,kind,title,category,audience,branchId?,teamId?,content,acknowledgementRequired,reason}. This creates a version-one unpublished suggestion. Employees can submit knowledge suggestions within own intended audience, with publication requiring C-027 independent current publisher approval (or reasoned Owner direct publication). SOP and MODULE authors require current library.manage authority. Content is structured bounded JSON blocks: TEXT {text}, IMAGE/PDF/VIDEO/FILE {fileId}, LINK {url,label}, CHECKLIST {items:[text]}, TEMPLATE {fileId}, SOP {versionId}. SOP references bind exact published accessible SOP versions. URLs are https/http only, displayed as links without server fetching or executing. Escape text in UI and forbid raw HTML/scripts. Kind/category labels cover the approved knowledge categories without requiring seed examples.

POST /api/v1/library/:id/versions accepts {commandId,expectedVersion,content,acknowledgementRequired,reason}. Retain earlier versions unchanged; only creator with still-valid author authority or current scoped management can append. Current audience remains fixed. LibraryPublication binds exact version, decision evidence and event; current published pointer must equal latest successful publication. C-027 governs SOP/knowledge publication. MODULE is authored/activated by scoped training management; it does not acquire an additional SOP/knowledge approval rule.

POST /api/v1/library/versions/:versionId/acknowledgements accepts {commandId,reason}. Only own active employee, exact published accessible version with acknowledgementRequired; retained once per employee/version. Acknowledging later versions never erases older acknowledgements.

POST /api/v1/library/references accepts {commandId,versionId,taskId?,templateVersionId?,reason}. Exactly one target; exact published SOP version only. Task reference requires current target-task management authority; template reference requires existing template management authority and exact immutable template version. Read references only where both target and SOP remain accessible; hiding a revoked SOP retains reference/history but exposes no restricted content. This sidecar does not rewrite applied template or task workflow/state.

Task management here means its current primary owner or Owner, or a current scoped assignment manager through TaskService.assertSopReferenceAuthority. New references are denied for completed/stopped/reassignment work and held/terminal delivery projects; currently authorized separate closeout work retains normal task authority. Collaborator/read-only access alone cannot add references.

Library files use library-owned immutable NAS blobs and stored checksum, MIME, byte count, safe filename and uploader/record ownership. Upload/read authorization belongs to LibraryService, not the storage adapter. Initial uploads attach to a record the actor may author/manage; finalized files may appear only in a version of that same record. Each stream repeats active session, current audience and exact readable version/file relationship. No detached, foreign-record, unpublished-file or cross-audience URL grants. Reads return no-store and safe Content-Disposition; never expose raw NAS storage keys. Files remain retained; no new expiry/deletion policy is invented. NAS failures are visible/retryable and metadata never claims missing bytes exist. Reuse chunked upload/checksum/staging safety from NasStorage in isolated .sense-library root; no external fetch/cloud duplication.

All library transitions have expected versions/idempotent command receipts and atomic canonical audit/domain/outbox. Immutable version/publication/ack/reference/file rows carry organization-specific foreign keys. Exact content snapshots and important acknowledgements survive current-pointer changes. Runtime cannot alter audience identity or overwrite historical evidence.
